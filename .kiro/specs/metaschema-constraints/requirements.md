# Requirements Document

## Introduction

GitHub issue #20. The server exposes OSCAL structure only through the generated JSON and XSD schemas (`get_oscal_schema`). Much of OSCAL's meaning lives in Metaschema constraints that the generated schemas do not carry: allowed prop names and values (e.g. `asset-type` on `defined-component`, which appears zero times in the 1.2.3 component JSON schema), UUID reference targets (`index` / `index-has-key`), co-occurrence and cardinality rules (`expect`, `has-cardinality`), and full documentation (`formal-name`, `description`, `remarks`). An agent cannot answer common modeling questions from primary sources today; `text_search_oscal` and `query_oscal_documentation` return no results for `asset-type`.

This feature bundles the NIST OSCAL Metaschema sources for the bundled OSCAL release (the `src/metaschema/oscal_*_metaschema.xml` modules and the `src/metaschema/shared-constraints/*.ent` entity files from the `usnistgov/OSCAL` tag that matches the bundled schemas), verifies them at startup like `oscal_schemas/`, and exposes them through size-bounded query tools.

Scope is split into two tiers:

- **Core (first slice, Requirements 1-7, plus Requirement 12 for `get_allowed_values`):** bundled, hash-verified, version-matched Metaschema sources and the `get_allowed_values` tool proposed by the owner on 2026-10-12.
- **Extended (Requirements 8-11, plus Requirement 12 for the extended tools):** `get_constraints`, `find_references_to`, `get_definition`, and a raw Metaschema source fallback. These reuse the core data and can ship in later PRs under the same issue.

A threat model (`threat-model.tc.json` in this spec directory, Threat Composer format; triage in design.md "Threat Model") informed the update-pinning, loader-limit, markup-safety, suggestion-cost, and error-disclosure criteria added by RC-9 to RC-13.

Facts checked against OSCAL v1.2.3 while writing this document: `src/metaschema/` holds 14 `oscal_*_metaschema.xml` module files (largest `oscal_assessment-common_metaschema.xml`, ~149 KB) and `shared-constraints/` holds 12 `.ent` files. Modules declare external entities in a `DOCTYPE` (e.g. `<!ENTITY allowed-values-component-type SYSTEM "./shared-constraints/allowed-values-component-type.ent">`) and include them inside `allowed-values` elements. Modules import other modules (`<import href="oscal_implementation-common_metaschema.xml"/>`). Each module declares `<schema-version>1.2.3</schema-version>`. Constraint targets are Metapath expressions relative to the declaring definition, and include predicates (`prop[has-oscal-namespace('http://csrc.nist.gov/ns/oscal')]/@name`), self-predicates (`(.)[@type='service']/link/@rel`), unions (`a|b`), descendant steps (`//`), and `doc(...)` calls. Some constraints have no `target` attribute because they are declared on a flag definition. For example, `oscal-component-type` is declared on the global flag `defined-component-type`, which `defined-component` references as its `type` flag through `<flag ref="defined-component-type"><use-name>type</use-name></flag>`.

## Glossary

- **Server**: The `mcp-server-for-oscal` MCP server process started by `main.main()`.
- **Metaschema_Source**: One NIST OSCAL Metaschema module file (`oscal_*_metaschema.xml`) or shared-constraints entity file (`*.ent`) from `usnistgov/OSCAL` at tag `v<Bundled_OSCAL_Version>`.
- **Metaschema_Bundle**: The package directory `src/mcp_server_for_oscal/oscal_metaschema/` holding all Metaschema_Sources, a `shared-constraints/` subdirectory, a `README.md` stating provenance, and a `hashes.json` manifest per directory.
- **Manifest_Allowlist**: The set of bundle-relative file paths listed in the two Metaschema_Bundle `hashes.json` manifests.
- **Bundled_OSCAL_Version**: The value returned by `utils.get_bundled_oscal_version()`, derived from the bundled JSON schema `$id`.
- **Update_Script**: The script run by `hatch run update-oscal-schemas` (`bin/update-oscal-schemas.sh`) or a companion script it invokes, driven by `CURRENT_RELEASE_VERSION` and `CURRENT_RELEASE_COMMIT`.
- **CURRENT_RELEASE_COMMIT**: The full 40-character lowercase hexadecimal commit SHA declared next to `CURRENT_RELEASE_VERSION` in `bin/update-oscal-schemas.sh`; the commit that tag `v$CURRENT_RELEASE_VERSION` of `usnistgov/OSCAL` points to.
- **Commit_Archive**: The `usnistgov/OSCAL` source archive for one commit, `https://github.com/usnistgov/OSCAL/archive/<commit>.zip`, whose zip comment is the full commit SHA.
- **Client_Facing_Message**: Any message passed to `try_notify_client_error`, and the text of any exception that a Metaschema_Tool raises to the caller, including the text of recorded load errors that a MetaschemaLoadError carries.
- **Metaschema_Index**: The in-memory or persisted representation of definitions and constraints parsed from the Metaschema_Bundle, used by all Metaschema_Tools. The Metaschema_Index is an immutable in-memory index, parsed from the Metaschema_Bundle once per process on first use (warmed at startup), and shared across threads.
- **MetaschemaLoadError**: The exception type, a subclass of `ValueError`, that Metaschema_Tools raise for Metaschema_Index load failures.
- **Metaschema_Tools**: The MCP tools defined by this feature: `get_allowed_values`, `get_constraints`, `find_references_to`, `get_definition`, and `get_metaschema_source`.
- **Model_Name**: An `OSCALModelType` value (e.g. `component-definition`, `system-security-plan`). Each Model_Name maps to one top-level Metaschema module (e.g. `component-definition` → `oscal_component_metaschema.xml`).
- **Model_Scope**: The top-level module for a Model_Name plus every module reachable from it through `<import>`, transitively.
- **Definition**: A Metaschema `define-assembly`, `define-field`, or `define-flag`, either global or inline (local) within another Definition.
- **Flag_Slot**: A flag of a Definition, declared either as an inline `define-flag` or as a `<flag ref="X">` reference to the global flag Definition `X`. The effective name of a Flag_Slot is its `use-name` if declared, else the inline flag's `name` or the reference's `ref`.
- **Constraint**: A Metaschema constraint element: `allowed-values`, `matches`, `index`, `index-has-key`, `is-unique`, `has-cardinality`, or `expect`.
- **Constraint_Target**: The `target` attribute of a Constraint, a Metapath expression relative to the declaring Definition. A Constraint with no `target` attribute has Constraint_Target `.`.
- **Target_Selector**: The `target` argument a caller passes to a Metaschema_Tool. Syntax: `<definition-name>` optionally followed by `/` and a path, or by a descendant step `//` and a path, e.g. `defined-component/@type`, `defined-component/prop/@name`, `system-component/link/@rel`, `part//part/@name`. A Target_Selector never contains predicates or unions.
- **Normalized_Path**: One alternative of a Constraint_Target (split on top-level `|`) with all predicates (`[...]`) and leading self steps (`(.)`, `.`) removed. A descendant step is kept as `//`. Examples: `(.)[@type='service']/link/@rel` → `link/@rel`; `.//by-component` → `//by-component`. An alternative that starts with `doc(...)` is a Cross_Document_Alternative.
- **Cross_Document_Alternative**: A Constraint_Target alternative that starts with a `doc(...)` call. A Cross_Document_Alternative never matches a Target_Selector; only `find_references_to` uses Cross_Document_Alternatives.
- **Namespace_Condition**: A top-level `and` conjunct of a predicate that has no top-level `or`, where the conjunct is exactly `has-oscal-namespace('<uri>')` or `has-namespace('<uri>')` with one string literal argument. A call with a sequence argument (e.g. `has-oscal-namespace(('uri1', 'uri2'))`) is not a Namespace_Condition. The `namespace` of a Normalized_Path alternative is the URI of the Namespace_Condition on the last step that has one.
- **Condition**: Predicate text removed from a step while computing a Normalized_Path and reported verbatim with the step it applied to (e.g. `{"step": "(.)", "predicate": "@type='service'"}`). On the last step that has a Namespace_Condition, the Condition is the remaining top-level `and` conjuncts of that predicate joined with ` and ` (no Condition if none remain). Every other predicate, including predicates with top-level `or`, predicates with sequence-argument namespace calls, and Namespace_Conditions on earlier steps, is a Condition verbatim.
- **Allowed_Value_Item**: One result item from `get_allowed_values`, describing one `enum` value of one `allowed-values` Constraint.
- **Source_Location**: The pair `source-file` (path relative to the Metaschema_Bundle, e.g. `shared-constraints/allowed-values-component-type.ent`) and `line` (1-based line number in that file where the cited element starts).
- **Page_Response**: The envelope returned by `utils.paginate()`: `items`, `total`, `offset`, `limit`, `hasMore`.
- **Response_Budget**: 20,000 characters, the maximum serialized JSON length of any single Metaschema_Tool response.

## Requirements

### Core (first slice)

### Requirement 1: Bundle Metaschema sources

**User Story:** As a maintainer, I want the Metaschema sources for the bundled OSCAL release shipped with the package, so that agents can query constraints offline and cite them exactly.

#### Acceptance Criteria

1. THE Metaschema_Bundle SHALL contain one Metaschema_Source for each `oscal_*_metaschema.xml` file in `src/metaschema/` and each `.ent` file in `src/metaschema/shared-constraints/` of `usnistgov/OSCAL` at tag `v<Bundled_OSCAL_Version>` (e.g. tag `v1.2.3` for Bundled_OSCAL_Version `1.2.3`, giving 14 module files and 12 entity files), and each file's bytes SHALL be identical to the tagged upstream file, including line endings.
2. THE Metaschema_Bundle SHALL contain no files other than the Metaschema_Sources from criterion 1, the `README.md` from criterion 4, and the `hashes.json` manifests from Requirement 2.
3. THE Metaschema_Bundle SHALL keep module files at its top level and entity files in its `shared-constraints/` subdirectory, so that every external entity `SYSTEM` path and every `<import href>` in every module resolves to an existing file inside the Metaschema_Bundle.
4. THE Metaschema_Bundle `README.md` SHALL state the source repository (`usnistgov/OSCAL`), the tag (`v<Bundled_OSCAL_Version>`), the commit as a line `Commit: <sha>` where `<sha>` is the CURRENT_RELEASE_COMMIT the Metaschema_Sources were downloaded from, and the retrieval date in `YYYY-MM-DD` format.
5. WHEN the repository is checked out on Linux, macOS, or Windows, THE checkout SHALL produce Metaschema_Bundle files that are byte-identical to the committed files, with no line-ending conversion, matching the existing treatment of `oscal_schemas/`.
6. WHEN the wheel is built, THE built wheel SHALL include every file from criteria 1, 2, and 4, at the same paths relative to the Metaschema_Bundle and with bytes identical to the repository files.
7. THE test suite SHALL include a test that fails if any module's external entity `SYSTEM` path or `<import href>` does not resolve to a file in the Metaschema_Bundle, or if the Metaschema_Bundle contains a file not allowed by criterion 2.

### Requirement 2: Verify Metaschema bundle integrity

**User Story:** As a security-conscious operator, I want the bundled Metaschema sources hash-verified at startup, so that tampered constraint data is never served.

#### Acceptance Criteria

1. THE Metaschema_Bundle SHALL contain one `hashes.json` manifest in `oscal_metaschema/` and one in `oscal_metaschema/shared-constraints/`, in the format produced by `bin/update_hashes.py`. Each manifest SHALL list the SHA-256 hash of every regular file in its own directory except `hashes.json`.
2. WHEN `hatch run rehash` runs, THE rehash script SHALL regenerate both Metaschema_Bundle manifests from the current file contents and `git add` both manifests, so that `verify_package_integrity` succeeds on the unchanged Metaschema_Bundle immediately afterward.
3. WHEN the Server starts, THE Server SHALL verify the Metaschema_Bundle and its `shared-constraints/` subdirectory with `verify_package_integrity`, in the same startup step that verifies `oscal_schemas/`, before it registers any tool or serves any request.
4. IF Metaschema_Bundle verification fails, THEN THE Server SHALL log an error that names the failing file and directory, exit with status 2, and serve no Metaschema_Tool request, matching the behavior for an `oscal_schemas/` mismatch. Verification fails in any of these cases: a file's SHA-256 hash differs from its manifest entry; a file listed in a manifest is missing; a regular file other than `hashes.json` is present but not listed in its directory's manifest; a manifest is missing or is not valid JSON; or a manifest is not byte-identical to the canonical form written by `bin/update_hashes.py` (or has top-level keys other than `commit` and `file_hashes`).
5. WHEN the `oscal-agent` entry point (`oscal_agent.main()`) starts, THE `oscal-agent` entry point SHALL verify the Metaschema_Bundle under the same rules as criteria 3 and 4, in the same step that verifies `oscal_schemas/`, and SHALL exit with status 2 on failure.
6. THE test suite SHALL include tests that start verification against a copy of the Metaschema_Bundle and assert exit status 2 for each failure case in criterion 4, including one changed byte in a module file and one changed byte in a `shared-constraints/*.ent` file, and SHALL assert that verification passes on the unmodified bundled copy.

### Requirement 3: Match the bundled OSCAL version

**User Story:** As a maintainer, I want the Metaschema sources locked to the same OSCAL release as the bundled schemas, so that constraints and schemas never disagree.

#### Acceptance Criteria

1. WHEN `hatch run update-oscal-schemas` runs, THE Update_Script SHALL download the Metaschema_Sources from the Commit_Archive of CURRENT_RELEASE_COMMIT (never from a tag or branch URL), over HTTPS with the default certificate and host-name verification, in the same run and with the same `CURRENT_RELEASE_VERSION` value that the run uses for the JSON and XSD schemas. CURRENT_RELEASE_COMMIT SHALL be the commit that tag `v$CURRENT_RELEASE_VERSION` points to.
2. WHEN the Update_Script has downloaded and checked the Metaschema_Sources without error, THE Update_Script SHALL replace the contents of the Metaschema_Bundle so that it contains exactly the `oscal_*_metaschema.xml` and `shared-constraints/*.ent` files present in the Commit_Archive, SHALL remove any Metaschema_Source that is not present in the Commit_Archive, and SHALL update the Metaschema_Bundle `README.md` with the tag, the commit, and the retrieval date.
3. IF CURRENT_RELEASE_COMMIT is not exactly 40 lowercase hexadecimal characters, the download does not complete within 300 seconds, the download returns an error, extraction fails, the zip comment of the downloaded Commit_Archive is not exactly CURRENT_RELEASE_COMMIT, or the extracted content holds zero `oscal_*_metaschema.xml` files or zero `.ent` files, THEN THE Update_Script SHALL exit with a non-zero status, SHALL print an error message naming the failed step, and SHALL leave every existing Metaschema_Bundle file byte-identical, with no files added or removed.
4. IF any downloaded module declares a `<schema-version>` that is not equal to `CURRENT_RELEASE_VERSION`, THEN THE Update_Script SHALL exit with a non-zero status, SHALL print an error message naming the module and its declared version, and SHALL leave every existing Metaschema_Bundle file byte-identical, with no files added or removed.
5. THE Update_Script SHALL write each Metaschema_Source byte-identical to the tagged upstream file, with no whitespace, indentation, or line-ending changes (unlike the minification applied to the bundled JSON schemas), so that Source_Location line numbers match the tagged upstream files.
6. THE test suite SHALL include a guard test that fails if the Metaschema_Bundle contains zero modules, or if any module in the Metaschema_Bundle does not declare exactly one `<schema-version>` equal to Bundled_OSCAL_Version. The failure message SHALL name each offending module and the version it declares.
7. THE test suite SHALL include a guard test that fails unless the tag stated in the Metaschema_Bundle `README.md` equals `v<Bundled_OSCAL_Version>`.
8. THE test suite SHALL include a guard test that fails unless the CURRENT_RELEASE_COMMIT declared in `bin/update-oscal-schemas.sh` is exactly 40 lowercase hexadecimal characters and equals the `<sha>` of the `Commit: <sha>` line in the Metaschema_Bundle `README.md`.

### Requirement 4: Resolve Metaschema entities and imports safely

**User Story:** As a developer, I want the Metaschema parser to expand shared-constraints entities and follow imports, so that values such as `provided-by` and `used-by` that live only in `.ent` files (e.g. `shared-constraints/allowed-values-component_component_service.ent`) are returned, without opening an XXE path.

#### Acceptance Criteria

1. WHEN a module references an external entity whose `SYSTEM` identifier is a relative path that resolves to a file inside the Metaschema_Bundle and in the Manifest_Allowlist, THE Metaschema_Index SHALL include the Constraints and enum values contained in that entity file at the position of the entity reference, in the same document order as if the entity file content were inlined at that position.
2. IF a module declares an external entity or an `<import href="...">` whose path is absolute, contains a URL scheme (for example `http:`, `https:`, `file:`), resolves (after normalizing `..` segments and following symbolic links) to a location outside the Metaschema_Bundle, or resolves to a bundle-relative path that is not in the Manifest_Allowlist, THEN THE Metaschema_Index SHALL not open the referenced location and SHALL record a load error naming the module file and the entity name or `href` value.
3. THE Metaschema_Index SHALL load all Metaschema_Sources without opening any network connection, and SHALL refuse to expand any internal entity whose replacement text contains a reference to another entity (billion-laughs protection), recording a load error naming the module file and the entity name.
4. WHEN a module contains `<import href="...">` whose `href` resolves to a module inside the Metaschema_Bundle, THE Metaschema_Index SHALL include the imported module and every module it imports, transitively, in the importing module's Model_Scope, resolving `href` relative to the Metaschema_Bundle.
5. THE Metaschema_Index SHALL report the Source_Location of an enum value or Constraint that originates in an entity file as that entity file (path relative to the Metaschema_Bundle) and the 1-based line of the element's start tag in that file, and SHALL report a Source_Location originating in a module as that module and the 1-based line of the element's start tag in that module, with line numbers counted against the unmodified bundled file.
6. IF a module references an external entity or an `<import href="...">` that resolves inside the Metaschema_Bundle but names a file that does not exist, THEN THE Metaschema_Index SHALL record a load error naming the module file and the missing path as a bundle-relative path or as the `SYSTEM` identifier or `href` value as written in the module, under the disclosure rules of criterion 11.
7. WHEN the imports reachable from a module form a cycle, or a module is reachable through more than one import path, THE Metaschema_Index SHALL include each module exactly once in the Model_Scope and SHALL finish loading without error for that reason.
8. IF the Metaschema_Index has recorded a load error for any module in the Model_Scope of a Metaschema_Tool call, THEN THE Metaschema_Tool SHALL call `try_notify_client_error` and raise MetaschemaLoadError naming the module and the entity, import, or limit that failed, under the disclosure rules of criterion 11, and SHALL return no partial results.
9. IF a module declares a parameter entity, or an entity file contains an external entity reference, THEN THE Metaschema_Index SHALL refuse to expand that entity, SHALL not open any location it names, and SHALL record a load error naming the module file and the entity name.
10. IF a Manifest_Allowlist file that the Metaschema_Index reads is larger than 2 MiB (2,097,152 bytes), or the element nesting depth in a module exceeds 64 (counting the elements of each included entity file at the depth of its entity reference), THEN THE Metaschema_Index SHALL stop parsing that module, SHALL exclude that module from every Model_Scope, and SHALL record a load error naming the module file, the entity file when the limit is reached inside an entity file, and the limit that was exceeded.
11. THE Metaschema_Index and every Metaschema_Tool SHALL compose each Client_Facing_Message only from bundle-relative paths or module file names, entity names, `href` and `SYSTEM` values as written in the module, and a statement of the rule broken, and SHALL write absolute filesystem paths, OS exception text that embeds a path, exception reprs, and tracebacks only to the server log, so that no Client_Facing_Message contains an absolute filesystem path, OS exception text that embeds a path, an exception repr, or a traceback.

### Requirement 5: get_allowed_values tool

**User Story:** As an AI assistant, I want the allowed values for a specific Metaschema context, so that I can answer questions such as "Is `asset-type` an OSCAL prop on `defined-component`, and are other values allowed?" from primary sources.

#### Acceptance Criteria

1. THE Server SHALL provide an MCP tool named `get_allowed_values` with parameters `model` (Model_Name, required), `target` (Target_Selector, required, 1 to 512 characters), `offset` (integer, default 0), `limit` (integer, default 25), and `ctx` (`Context | None`, default `None`).
2. WHEN `get_allowed_values` is called with a valid `model` and `target`, THE `get_allowed_values` tool SHALL return a Page_Response whose `items` hold one Allowed_Value_Item per `enum` value of each `allowed-values` Constraint that meets all of these conditions: the Constraint is within the Model_Scope, it is declared on a Definition whose name equals the first segment of the Target_Selector, and one of its Normalized_Path alternatives that is not a Cross_Document_Alternative equals the remainder of the Target_Selector. The remainder is the text after the first segment, without its leading `/` when the text after the first segment starts with a single `/`, and with its leading `//` kept when that text starts with `//` (e.g. `part//part/@name` has remainder `//part/@name`). Comparison is exact and case-sensitive.
3. WHEN the Target_Selector has no `/` (a bare definition name), THE `get_allowed_values` tool SHALL treat the remainder as empty and SHALL match only `allowed-values` Constraints whose Normalized_Path is empty (Constraint_Target `.` or no `target` attribute).
4. WHEN the Target_Selector is `<name>/@<flag>` and the Definition `<name>` has a Flag_Slot whose effective name equals `<flag>`, THE `get_allowed_values` tool SHALL also return the Allowed_Value_Items of the `allowed-values` Constraints whose Normalized_Path is empty and that are declared on that Flag_Slot's flag Definition: the inline flag Definition for an inline `define-flag`, or, for a `<flag ref="X">`, the global flag Definition named `X` in the Model_Scope.
5. WHEN one `allowed-values` Constraint matches the Target_Selector through more than one Normalized_Path alternative, THE `get_allowed_values` tool SHALL return each of its `enum` values once.
6. THE `get_allowed_values` tool SHALL resolve the Definition by its definition name as declared in the Metaschema (e.g. `defined-component`, `system-component`), so that `defined-component/@type` and `system-component/@type` each return only the values of their own Constraints. WHEN more than one Definition in the Model_Scope has that name (e.g. a global Definition and a local Definition), THE `get_allowed_values` tool SHALL include matches from all of them, and the Source_Location of each item SHALL identify the declaring Definition's source, with the flag Definition named by `flag-definition` (Requirement 6 criterion 13) for matches made through criterion 4.
7. THE `get_allowed_values` tool SHALL order items by the Constraint's `source-file` (ascending, case-sensitive string order), then by the Constraint's `line` (ascending), then by the document order of the `enum` value in the Constraint, so that repeated calls with the same arguments against the same Metaschema_Bundle return identical items in identical order.
8. WHEN the Target_Selector names a Definition in the Model_Scope and no `allowed-values` Constraint matches, THE `get_allowed_values` tool SHALL return a Page_Response with an empty `items` list, `total` 0, `hasMore` `false`, and a `suggested-targets` list. The list SHALL hold 0 to 20 distinct Target_Selectors in ascending string order, each formed from that Definition's name and either a non-cross-document Normalized_Path alternative of an `allowed-values` Constraint on that Definition (`<name>` for an empty path, `<name><path>` for a path that starts with `//`, else `<name>/<path>`) or the effective name of a Flag_Slot whose flag Definition declares an `allowed-values` Constraint with an empty Normalized_Path (`<name>/@<flag>`), where each one returns at least 1 item when passed back as `target`.
9. IF `model` is not exactly an `OSCALModelType` value, THEN THE `get_allowed_values` tool SHALL call `try_notify_client_error` and raise `ValueError` that names the invalid model value and refers the caller to `list_oscal_models`.
10. IF the first segment of the Target_Selector does not name a Definition in the Model_Scope, THEN THE `get_allowed_values` tool SHALL call `try_notify_client_error` and raise `ValueError` that names the unknown segment, truncated to its first 80 characters, and lists 1 to 10 Definition names from the Model_Scope. The names SHALL be ordered by ascending case-insensitive edit distance to the first 64 characters of the segment, with ties broken by ascending string order.
11. IF `target` is empty, longer than 512 characters, starts or ends with `/`, contains `///`, contains any whitespace character, or contains any of the characters `[`, `]`, `(`, `)`, or `|`, THEN THE `get_allowed_values` tool SHALL call `try_notify_client_error` and raise `ValueError` that names the malformed Target_Selector and states the syntax rule it breaks, without searching the Metaschema_Index.
12. IF `offset` is less than 0, or `limit` is less than 1 or greater than `utils.MAX_PAGE_LIMIT` (100), THEN THE `get_allowed_values` tool SHALL raise the `ValueError` produced by `utils.paginate`. WHEN `offset` is greater than or equal to `total`, THE `get_allowed_values` tool SHALL return an empty `items` list with the unchanged `total` and `hasMore` `false`. WHEN the page at the requested `limit` would exceed the Response_Budget, THE `get_allowed_values` tool SHALL return a shorter page and report the reduced `limit` as specified in Requirement 12 criterion 4.
13. IF the Metaschema_Index cannot be loaded for the Model_Scope (for example, because of an entity refused under Requirement 4 criterion 2 or criterion 9, a size or nesting limit exceeded under Requirement 4 criterion 10, or a malformed Metaschema_Source), THEN THE `get_allowed_values` tool SHALL call `try_notify_client_error` and raise MetaschemaLoadError that names the failing Metaschema_Source by its bundle-relative path, under the disclosure rules of Requirement 4 criterion 11, and SHALL return no partial items.

### Requirement 6: Allowed_Value_Item content

**User Story:** As an AI assistant, I want each allowed value to carry its meaning, openness, namespace, conditions, and source, so that I can tell an OSCAL prop from a third-party prop and cite the Metaschema directly.

#### Acceptance Criteria

1. THE Allowed_Value_Item SHALL contain the keys `value`, `description`, `allow-other`, `definition`, `target`, `level`, `source-file`, and `line`, where `value` is the enum element's `value` attribute verbatim, `definition` is the name of the Definition that declares the Constraint (for a Constraint on a Flag_Slot's flag Definition, inline or referenced, the name of the Definition that has the Flag_Slot, as written in the Target_Selector's first segment), and `target` is the original Constraint_Target verbatim (`.` when the Constraint has no `target` attribute).
2. THE Allowed_Value_Item SHALL report `allow-other` as JSON `true` when the Constraint's `allow-other` attribute is `yes`, and as JSON `false` when the attribute is `no` or absent (the Metaschema default `no`).
3. WHERE the Constraint declares an `extensible` attribute, THE Allowed_Value_Item SHALL include `extensible` with the attribute value verbatim (one of `model`, `external`, or `none`); WHERE the Constraint has no `extensible` attribute, THE Allowed_Value_Item SHALL omit the `extensible` key.
4. WHERE the Normalized_Path alternatives through which the Constraint matched have exactly one distinct `namespace` among them, THE Allowed_Value_Item SHALL include `namespace` with that Namespace_Condition's URI verbatim, and SHALL NOT repeat that Namespace_Condition in the `conditions` list; WHERE the matched alternatives have no `namespace` or more than one distinct `namespace`, THE Allowed_Value_Item SHALL omit the `namespace` key and SHALL report each Namespace_Condition as a Condition.
5. WHERE the matched Normalized_Path alternatives have one or more Conditions, THE Allowed_Value_Item SHALL include a `conditions` list with one entry per distinct Condition, each holding the Condition's `step` and `predicate` text verbatim, in the order the Conditions appear in the Constraint_Target, so that `(.)[@type='service']/link/@rel` values are distinguishable from unconditional `link/@rel` values; WHERE no such Condition exists, THE Allowed_Value_Item SHALL omit the `conditions` key.
6. WHERE the enum element declares a `deprecated` attribute, THE Allowed_Value_Item SHALL include `deprecated` with the attribute value verbatim; WHERE the enum element has no `deprecated` attribute, THE Allowed_Value_Item SHALL omit the `deprecated` key.
7. THE Allowed_Value_Item SHALL render the enum's description as plain text under these rules, applied in order:
   - C0 control characters (U+0000 to U+001F) other than tab (U+0009) and newline (U+000A) are removed from the text before whitespace handling.
   - Inline Metaschema markup becomes Markdown: `code` → `` `text` ``, `q` → `"text"`, `em` → `*text*`, `strong` → `**text**`.
   - An `a` element becomes `[text](href)` only when its `href` is an absolute URL with scheme `http` or `https` (case-insensitive), a fragment starting with `#`, or a relative reference with no scheme (no `:` before the first `/`, `?`, or `#`) that does not start with `//`. In that case, `\`, `[`, and `]` in the link text are backslash-escaped, and `(`, `)`, `<`, `>`, and every character at or below U+0020 in the `href` are percent-encoded. For any other `href` (for example `javascript:`, `data:`, `file:`, `mailto:`, `//host`, empty, or missing), only the link text is emitted.
   - Any other element is replaced by its text content.
   - Each run of whitespace is collapsed to one space, and leading and trailing whitespace is removed.
8. IF the enum element has no text content, THEN THE Allowed_Value_Item SHALL report `description` as an empty string.
9. THE Allowed_Value_Item SHALL contain no null values and SHALL use hyphenated keys, matching Metaschema attribute names and the repo's OSCAL JSON convention.
10. THE `level` key SHALL hold the Constraint's `level` attribute verbatim (one of `CRITICAL`, `ERROR`, `WARNING`, `INFORMATIONAL`, or `DEBUG`), using `ERROR` when the attribute is absent (the Metaschema default).
11. WHERE the Constraint declares an `id` attribute, THE Allowed_Value_Item SHALL include `constraint-id` with that value verbatim; WHERE the Constraint has no `id` attribute, THE Allowed_Value_Item SHALL omit the `constraint-id` key.
12. THE Allowed_Value_Item SHALL report `source-file` and `line` as the Source_Location of the enum element (not of the enclosing `allowed-values` Constraint), so that the line at `source-file`:`line` contains the item's `value` as required by Requirement 7 criterion 8.
13. WHERE the Constraint matched through a Flag_Slot under Requirement 5 criterion 4 (inline or referenced), THE Allowed_Value_Item SHALL include `flag-definition` with the name of the flag Definition that declares the Constraint (e.g. `defined-component-type`); WHERE the Constraint did not match through a Flag_Slot, THE Allowed_Value_Item SHALL omit the `flag-definition` key.

### Requirement 8: get_constraints tool

**User Story:** As an AI assistant, I want every constraint that applies at a path, so that I can explain co-occurrence, cardinality, datatype, uniqueness, and reference rules that the JSON schema does not express.

#### Acceptance Criteria

1. THE Server SHALL provide an MCP tool named `get_constraints` with parameters `model` (Model_Name), `target` (Target_Selector), `constraint_types` (optional list of Constraint element names, default none), `offset` (default 0), `limit` (default 25), and `ctx` (`Context | None`).
2. WHEN `get_constraints` is called with a Target_Selector that contains a `/` after the definition name, THE `get_constraints` tool SHALL return a Page_Response whose `items` are every Constraint within the Model_Scope that matches the Target_Selector under the matching rules of Requirement 5 criteria 2, 4, 5, and 6, applied to all seven Constraint element types instead of `allowed-values` only.
3. WHEN `get_constraints` is called with a Target_Selector that is a bare definition name (no `/`), THE `get_constraints` tool SHALL return a Page_Response of every Constraint declared on that Definition and on every inline Definition nested within it at any depth, whatever the Constraint_Target.
4. WHEN `constraint_types` is a non-empty list, THE `get_constraints` tool SHALL return only Constraints whose element name is in `constraint_types`. WHEN `constraint_types` is omitted or an empty list, THE `get_constraints` tool SHALL apply no type filter.
5. THE `get_constraints` tool SHALL order items by the Source_Location of the Constraint (`source-file`, then `line`), so that repeated calls with the same arguments return the same items in the same order.
6. THE `get_constraints` result item SHALL contain `type` (the Constraint element name), `definition`, `target` (the original Constraint_Target, or `.` when the attribute is absent), `level` (using `ERROR` when the attribute is absent), `source-file`, and `line`, plus `constraint-id` when the Constraint has an `id`. The item SHALL contain these type-specific keys when the Constraint declares the matching attribute or child element, and SHALL omit them otherwise: for `allowed-values`, `allow-other` (boolean, `false` when absent), `extensible`, and `value-count` (the number of enum values after entity expansion); for `matches`, `datatype` and `regex`; for `index`, `index-has-key`, and `is-unique`, `name` (not for `is-unique`) and `key-fields` (the `target` values of the Constraint's `key-field` elements, in document order); for `has-cardinality`, `min-occurs` and `max-occurs`; and for `expect`, `test` and `message`. The item SHALL follow the content rules of Requirement 6 criterion 9: hyphenated keys and no null values.
7. THE `get_constraints` result item SHALL include `namespace` and `conditions` under the same rules as Requirement 6 criteria 4 and 5.
8. WHEN the Target_Selector names an existing Definition and no Constraint matches the Target_Selector and `constraint_types`, THE `get_constraints` tool SHALL return a Page_Response with an empty `items` list and `total` 0.
9. IF `constraint_types` contains a value that is not one of the seven Constraint element names, THEN THE `get_constraints` tool SHALL call `try_notify_client_error` and raise `ValueError` that names each invalid value and lists the seven valid names. The tool SHALL return no items.
10. IF `model` is not a Model_Name, or the first segment of the Target_Selector does not name a Definition in the Model_Scope, THEN THE `get_constraints` tool SHALL call `try_notify_client_error` and raise `ValueError` with the content specified in Requirement 5 criterion 9 or criterion 10, respectively.
11. IF `offset` or `limit` is outside the range that `utils.paginate` accepts, THEN THE `get_constraints` tool SHALL raise the `ValueError` that `utils.paginate` produces.

### Requirement 9: find_references_to tool

**User Story:** As an AI assistant, I want every field or prop that must resolve to a given assembly, so that I can answer "what in an SSP refers to a `system-component` by UUID?" including prop-based references that field-name matching misses.

#### Acceptance Criteria

1. THE Server SHALL provide an MCP tool named `find_references_to` with parameters `assembly` (a definition name, or the last step of an `index` Normalized_Path, e.g. `component`), `model` (optional Model_Name; all modules in the Metaschema_Bundle when omitted), `offset` (default 0), `limit` (default 25), and `ctx` (`Context | None`).
2. WHEN `find_references_to` is called, THE `find_references_to` tool SHALL select every `index` Constraint in the Metaschema_Bundle that has a Normalized_Path alternative whose last step equals `assembly`, or equals the `use-name` of a Definition named `assembly`, using exact, case-sensitive string comparison.
3. WHEN `find_references_to` is called, THE `find_references_to` tool SHALL return a Page_Response with one item for each pair of a selected `index` Constraint and an `index-has-key` Constraint whose `name` equals that `index` Constraint's `name`. WHERE `model` is given, the tool SHALL consider only `index-has-key` Constraints declared within the Model_Scope of `model`.
4. THE `find_references_to` result item SHALL contain `index-name`; the `index-has-key` Constraint's `definition`, `target` (the original Constraint_Target), `key-fields` (the `target` of each key field, in document order), `source-file`, and `line`; and the `index` Constraint's `definition`, `target`, `source-file`, and `line` under the hyphenated keys `index-definition`, `index-target`, `index-source-file`, and `index-line`. The item SHALL use hyphenated keys and SHALL contain no null values.
5. THE `find_references_to` result item SHALL include `namespace` and `conditions` for the `index-has-key` Constraint_Target under the same rules as Requirement 6 criteria 4 and 5, and SHALL omit each key when no matching Condition exists.
6. WHEN an `index-has-key` Constraint names an `index` declared in a module other than the one that declares the `index-has-key` Constraint, THE `find_references_to` tool SHALL resolve the `index` across all modules in the Metaschema_Bundle, regardless of `model`.
7. THE `find_references_to` result item SHALL include `cross-document` as `true` if the `index` Constraint_Target contains a Cross_Document_Alternative, and as `false` otherwise.
8. WHEN no `index` Constraint matches `assembly`, including when `assembly` is an empty string, THE `find_references_to` tool SHALL return a Page_Response with an empty `items` list and `total` 0.
9. IF `model` is given and is not a Model_Name, THEN THE `find_references_to` tool SHALL call `try_notify_client_error` and raise `ValueError` naming the invalid model and pointing to `list_oscal_models`.
10. IF `offset` or `limit` is outside the range accepted by `utils.paginate`, THEN THE `find_references_to` tool SHALL raise the `ValueError` produced by `utils.paginate`.
11. THE `find_references_to` tool SHALL order items by the `index-has-key` Constraint's Source_Location (`source-file` ascending, then `line` ascending), then by `index-name`, so that repeated calls with the same arguments return the same order.

### Requirement 10: get_definition tool

**User Story:** As an AI assistant, I want one Definition with its full documentation and constraints, so that I can read the formal name, description, and remarks that the generated JSON schema shortens or drops.

#### Acceptance Criteria

1. THE Server SHALL provide an MCP tool named `get_definition` with parameters `model` (optional Model_Name), `name` (definition name, 1 to 200 characters), `kind` (optional; one of `assembly`, `field`, or `flag`), `offset` (integer, default 0), `limit` (integer, default 10), and `ctx` (`Context | None`).
2. WHEN `get_definition` is called, THE `get_definition` tool SHALL return a Page_Response whose `items` are the matches: every Definition whose name equals `name` (case-sensitive exact match) and whose kind equals `kind`. The search covers the Model_Scope of `model` when `model` is given and every module in the Metaschema_Bundle when `model` is omitted. When `kind` is omitted, the search covers all three kinds.
3. THE `get_definition` match SHALL contain `kind`, `name`, `scope` (`global` or `local`), `formal-name`, `description`, `remarks`, `use-name` and `group-as` (when declared), `flags` (each with name, `required`, and datatype), `model` children (each with name, kind, `min-occurs`, `max-occurs`, and `group-as`), a `constraints` summary (type, `constraint-id` when present, and `target` for each Constraint declared on that Definition), `source-file`, and `line`. The tool SHALL omit any key whose value the Metaschema does not declare, and the response SHALL contain no null values.
4. THE `get_definition` tool SHALL render `description` as plain text under the rules of Requirement 6 criterion 7, and SHALL render `remarks` as plain text that removes C0 control characters, converts inline Metaschema markup (`code`, `q`, `em`, `strong`) to Markdown, and renders `a` elements with the same `href` acceptance, link-text escaping, and `href` percent-encoding, all under the same rules, and that separates paragraphs with `\n\n` and starts each list item with `- `.
5. WHEN `name` matches more than one Definition (e.g. a global Definition and a local Definition with the same name in different modules), THE `get_definition` tool SHALL return all matches across its pages, ordered by Source_Location (`source-file`, then `line`). Each match SHALL be identified by `source-file`, and each local match SHALL also carry a `parent-definition` key that names its enclosing Definition.
6. IF the serialized `get_definition` page at the requested `limit` would exceed the Response_Budget, THEN THE `get_definition` tool SHALL return a shorter page as specified in Requirement 12 criterion 4, and IF the single match at `offset` alone would exceed the Response_Budget, THEN THE `get_definition` tool SHALL shorten that match's `remarks` until the response is at most Response_Budget characters, set `truncated` to `true` on that match, and keep the match's Source_Location, so that the caller can get the full text with `get_metaschema_source`.
7. IF `name` is empty, longer than 200 characters, or matches no Definition in the searched modules, THEN THE `get_definition` tool SHALL call `try_notify_client_error` and raise `ValueError` that lists up to 10 Definition names from the searched modules with the closest spelling to `name`, and SHALL return no partial result.
8. IF `model` is given and is not a Model_Name, THEN THE `get_definition` tool SHALL call `try_notify_client_error` and raise `ValueError` that names the invalid model and points to `list_oscal_models`.
9. IF `kind` is given and is not one of `assembly`, `field`, or `flag`, THEN THE `get_definition` tool SHALL call `try_notify_client_error` and raise `ValueError` that lists the three valid kinds.

### Requirement 11: Raw Metaschema source fallback

**User Story:** As an AI assistant, I want to read a bounded range of a bundled Metaschema file, so that I can verify a citation or read context that the query tools do not summarize, without overflowing my tool-result limit.

#### Acceptance Criteria

1. THE Server SHALL provide an MCP tool named `get_metaschema_source` with parameters `file` (optional; a path relative to the Metaschema_Bundle root, e.g. `oscal_component_metaschema.xml` or `shared-constraints/allowed-values-component-type.ent`), `start_line` (integer, 1-based, default 1), `line_count` (integer, 1 to 500, default 200), and `ctx` (`Context | None`).
2. WHEN `get_metaschema_source` is called with a `file` that exactly matches (case-sensitive) a path in the Manifest_Allowlist, and a `start_line` from 1 to that file's `total-lines`, THE `get_metaschema_source` tool SHALL return a dict with `file` (the bundle-relative path), `start-line` (equal to `start_line`), `end-line` (the smaller of `start_line + line_count - 1` and `total-lines`, subject to criterion 4), `total-lines`, `has-more` (`true` if and only if `end-line` is less than `total-lines`), and `text` holding lines `start-line` through `end-line` verbatim, including their original line terminators, with line numbering identical to the Source_Location `line` values reported by the other Metaschema_Tools.
3. IF `file` is not a path in the Manifest_Allowlist (including absolute paths, paths containing `..`, and URLs), THEN THE `get_metaschema_source` tool SHALL call `try_notify_client_error` and raise `ValueError` listing the available bundle-relative file paths, under the disclosure rules of Requirement 4 criterion 11, without opening any file.
4. IF the lines from `start_line` to the end-line computed in criterion 2 would make the serialized JSON response exceed the Response_Budget, THEN THE `get_metaschema_source` tool SHALL return the largest number of consecutive lines starting at `start_line` that keeps the response within the Response_Budget, set `has-more` to `true`, and report the last returned line number as `end-line`.
5. WHEN `get_metaschema_source` is called with `file` omitted, THE `get_metaschema_source` tool SHALL ignore `start_line` and `line_count` and return a dict with a `files` list containing one entry per file in the Manifest_Allowlist, each entry holding `file` (bundle-relative path) and `line-count`, sorted by `file` in ascending order.
6. IF `start_line` is less than 1 or greater than the `total-lines` of the requested `file`, THEN THE `get_metaschema_source` tool SHALL call `try_notify_client_error` and raise `ValueError` stating the valid range 1 to `total-lines` for that file.
7. IF `line_count` is less than 1 or greater than 500, THEN THE `get_metaschema_source` tool SHALL call `try_notify_client_error` and raise `ValueError` stating the valid range 1 to 500.

### Requirement 12: Size bounds for all Metaschema tools

**User Story:** As an AI assistant with a tool-result limit, I want every Metaschema tool response bounded, so that a query never overflows my context the way the ~93k-character SSP JSON schema does.

#### Acceptance Criteria

1. THE `get_allowed_values`, `get_constraints`, `find_references_to`, and `get_definition` tools SHALL return a Page_Response produced by `utils.paginate`, and SHALL accept an integer `offset` of 0 or greater and an integer `limit` from 1 to `utils.MAX_PAGE_LIMIT` (100) inclusive.
2. IF a list-returning Metaschema_Tool is called with an `offset` below 0 or a `limit` outside 1 to `utils.MAX_PAGE_LIMIT`, THEN THE Metaschema_Tool SHALL raise the `ValueError` produced by `utils.paginate` and SHALL return no Page_Response.
3. THE Server SHALL ensure that every Metaschema_Tool response, serialized as JSON, is at most Response_Budget (20,000) characters, for every argument combination that the Metaschema_Tool accepts without raising an error.
4. IF the items from `offset` at the requested `limit` would make the serialized Page_Response exceed the Response_Budget, THEN THE Metaschema_Tool SHALL return the longest prefix of those items that fits within the Response_Budget, set `limit` to the number of items returned, keep `total` equal to the full number of matching items, and set `hasMore` to `true` if and only if `offset` plus the number of items returned is less than `total`.
5. IF `offset` is less than `total` and the single item at `offset` alone would make the serialized Page_Response exceed the Response_Budget, THEN THE Metaschema_Tool SHALL return that one item with its free-text values shortened until the response fits, set `truncated` to `true` on that item, and keep the item's Source_Location so the caller can read the full text with `get_metaschema_source`. The free-text values are `description` for `get_allowed_values`, `message` and `test` for `get_constraints`, and `remarks` for `get_definition`.
6. WHEN a caller requests successive pages with each `offset` equal to the previous `offset` plus the number of items the previous page returned, starting at `offset` 0 and stopping when `hasMore` is `false`, THE Metaschema_Tool SHALL return every matching item exactly once, in the order defined by that tool's ordering criterion (Requirement 5 criterion 7 for `get_allowed_values`, Requirement 8 criterion 5 for `get_constraints`, Requirement 9 criterion 11 for `find_references_to`, Requirement 10 criterion 5 for `get_definition`), with each page holding at least one item.
7. WHEN a list-returning Metaschema_Tool is called with an `offset` equal to or greater than `total`, THE Metaschema_Tool SHALL return a Page_Response with an empty `items` list, the full `total`, and `hasMore` set to `false`.

## Resolved Questions

All questions raised during requirements refinement are resolved in design.md ("Key decisions"); the resulting requirement changes RC-1 to RC-8 are applied above. Requirement changes RC-9 to RC-13, from the threat model triage in design.md "Threat Model" (`threat-model.tc.json`), are also applied above: commit-pinned update (Requirement 1 criterion 4, Requirement 3 criteria 1, 2, 3, and 8), loader size and depth limits (Requirement 4 criterion 10), safe markup rendering (Requirement 6 criterion 7, Requirement 10 criterion 4), bounded suggestion cost (Requirement 5 criterion 10), and client-facing error disclosure (Requirement 4 criterion 11).

1. **Target matching semantics.** Resolved: structural matching on Normalized_Paths, with predicates reported as Conditions and `//` kept literally (design OQ1, RC-3).
2. **Constraints inherited from referenced Definitions.** Resolved: out of scope for the first slice; only Constraints on the named Definition and its Flag_Slots' flag Definitions are returned, and callers also query `property/@name` and `link/@rel` (design OQ2, RC-2). A `declared-on` key is left for a later slice.
3. **Line numbers and parser choice.** Resolved: stdlib `pyexpat` with one `ExternalEntityParserCreate` sub-parser per entity for per-file lines; no new dependency (design OQ3, RC-5).
4. **Runtime parse vs build-time index.** Resolved: runtime parse on first use into an immutable process-wide cache, warmed at startup; no build-time artifact (design OQ4).
5. **Key style.** Resolved: hyphenated item keys with the existing Page_Response envelope (`hasMore`) (design OQ5).
6. **Raw fallback shape.** Resolved: separate `get_metaschema_source` tool with line ranges; `get_oscal_schema` unchanged (design OQ6).
7. **Rendered OSCAL-Reference pages.** Resolved: out of scope (design OQ7).
8. **Tool naming.** Resolved: keep the issue's names without an `oscal` qualifier; docstrings name OSCAL Metaschema in their first sentence (design OQ8).
9. **Upstream source for the Update_Script.** Resolved: the Commit_Archive of CURRENT_RELEASE_COMMIT (the commit that tag `v<version>` points to), because the release zip has no `.ent` files and a pinned commit cannot move like a tag (design OQ9, RC-9).
10. **Implementation notes for design.** Resolved: `.gitattributes` `-text` entry for `oscal_metaschema/**`; no wheel config change needed; integrity `except` widened to `(RuntimeError, KeyError, OSError, ValueError)` through a shared helper; `rehash` gains the `oscal_metaschema` directory (design OQ10 a-d).
